## Single-segment joint audit, test and repair rule (owner decision, 2026-11-18)

**Mandatory for all subsequent BOT KING development; applies to timeframe, five filters, Scanner, Watchlist, Super Five, Option Chain, Oracle, authentication, APK and every other segment.** Work cautiously and finish one chosen segment before opening another.

1. **Identify and lock ONE segment.** Write down its name, exact user-visible faults, impacted functions/files/screens and the intended outcome. Give this batch a single segment ID and keep all directly related changes within it. Do not alternate between timeframe, filters, options and UI during the same batch.
2. **Audit the entire identified segment ONCE before editing.** Collect the available source, current branch SHA, last relevant changes and CI failures, API/cache/timeframe dependencies, and all known symptoms together. Mark a bounded checklist of affected points and unknowns; do not conduct a separate micro-audit for every file or newly noticed assertion. Reuse verified results rather than repeating old checks.
3. **Plan tests TOGETHER before fixing.** Determine the finite set of focused test cases and one integrated regression gate covering the entire segment: successful path, missing/error/429 cases, Dhan-only evidence/freshness, last-good retention, time/expiry/symbol isolation, and relevant UI context. Include only cases applicable to that segment. Record the test list and measurable PASS criteria before the first source edit.
4. **Apply ONE JOINT repair batch.** Group the necessary 2–4 directly related source/cache/UI/test updates after the complete review. Prefer one coherent source+test batch and one resulting GitHub CI run rather than one push/run per tiny edit. Preserve existing tested behavior and avoid out-of-segment feature work. Never weaken tests to conceal failures.
5. **Run the planned targeted tests and ONE combined regression at the pinned final source SHA.** Check all actual failed steps/logs. If it FAILS, fix only the proven cause inside the same locked segment and rerun that affected gate; do not start a different segment, unrelated test storm, or recursive AST audit.
6. **Close the segment before switching.** Mark `DONE` with exact SHA, test count, workflow result and limitations, or `BLOCKED` with the ONE missing prerequisite and safe next action. Update `docs/BOT_KING_WORK_LOG.md` and `docs/BOT_KING_LIVE_WORK_INDEX.md` together. Only then unlock and select the next segment. A blocked Oracle production deployment still requires explicit authorization; unrelated source CI does not convert it to DONE.
7. **Narrow exceptions:** If an urgent security/data-integrity issue is discovered outside scope, record it and either pause the locked segment explicitly or defer the new issue—never silently switch contexts. Existing CI runs may finish in parallel, but do not launch new fixes in another segment while the current segment's acceptance gate is unfinished. User `OK` means continue the current segment's next action, not jump to a new topic.

**Required segment register at start:** `SEGMENT | USER DEFECT/GOAL | AFFECTED POINTS | TEST LIST + PASS GATE | JOINT CHANGES | ACTUAL CI/ORACLE/PHONE RESULT | DONE/BLOCKED | NEXT`. This can be one compact row in the existing Live Work Index; do not create duplicate planning documents.

**Precedence:** This single-segment owner rule narrows earlier guidance about independent parallel *edits* and exploratory multi-lane fixes. Historical CI can continue running independently; one controlled writer and one active segment govern new repairs. All safety rules and separate Oracle deployment approval still apply.

## Parallel test-and-fix pipeline (continuous integration)
- A test run is immutable evidence for its own commit SHA. A completed PASS can be recorded immediately, while unrelated tests continue. A FAIL can enter the repair queue immediately after exact failed step/log/root-cause review; do not wait for all other tests to finish unless changes share code or caches.
- Keep three logical lanes: **Test lane** (GitHub CI on pinned SHAs), **Analysis lane** (read-only failures, coverage, risk, history), and **Fix lane** (one controlled writer for the shared branch). Independent CI/audit can overlap; never let multiple writers race on the same file or launch uncontrolled broker requests.
- Prioritize failures by blocker/security/data correctness, then missing coverage, then UI polish. Group failures with the same root cause into 2–4 related changes. Each fix requires a regression test and a new run on its resulting SHA. A previous PASS does not certify a later SHA.
- Maintain a live queue in the consolidated test matrix with **test ID, source SHA, run ID, status, failing step, owner action, fix SHA, retest run, and final gate**. Mark old running results as superseded only after verifying, never delete evidence. Limit CI fanout; use workflow concurrency behavior and resource caps, and avoid changing the release SHA while final joint regression is running.
- After all critical issues are repaired, freeze the release candidate SHA, run the full joint regression, verify integration gates and only then build a signed APK. Real-phone live-market verification remains separate. No autonomous post-turn work is implied unless an actual scheduled automation exists.

## Closure and reopening gate: finish work instead of perpetual retesting (owner rule, 2026-11-17)
- **Each scoped task must reach a terminal state**: `CLOSED — VERIFIED` (defined acceptance criteria passed with exact evidence), `CLOSED — LIMITED` (specific permitted scope passed while other separate end-to-end gates remain open), `BLOCKED` (named external prerequisite), or `DEFERRED` (owner pipeline). Use `IN PROGRESS` only while an actual step is unfinished. Clearly list a closed task's scope, check IDs, code SHA, test/workflow URL and any boundary not yet validated.
- **Once closed, do not keep working, retesting or polishing it by default**. Move directly to the next unresolved task. Existing successful evidence is enough for the exact same source, environment and acceptance scope. Avoid reopening work solely because more hypothetical tests could be invented.
- **Reopen only for a concrete reason**: a new feature/addition, changed relevant code/dependency/provider contract/configuration, new failure or field symptom, expired time-sensitive data, a documented credible technical suspicion, or an explicitly required previously-unverified integration/release gate. Log `REOPENED`, the triggering evidence/hypothesis and exact newly required scope. No unexplained or speculative retesting.
- **Keep task closure separate from global product release approval**. Closing a Watchlist source/CI task does not certify Oracle production, Dhan live market data, Android APK, phone or other untested integration; those remain separately named open/blocked tasks. Conversely an unrelated pending integration must not cause already verified source work to be marked perpetually unfinished.
- **One-pass loop:** identify issue -> fix in a coherent batch -> test until acceptance passes -> log closure -> proceed. If a later justified change affects this scope, reopen minimally, validate only affected checks first and record new closure. Do not equate a document-only change with runtime behavior change.
