## Confirmed release blocker: same Android package, different signing certificates (P0)
- B197 APK [Run 44941092536](https://github.com/vaishnavi596/volume-king/actions/runs/44941092536), job 136958244860: package `com.botking.sudhar1.bot_king_v1_pure_clone`, versionCode 197, actual apksigner `V2 Signer: certificate DN: C=US, O=Android, CN=Android Debug`, SHA-256 **a8cba963a95cd13a1ebc18321af3d876fc07a44fee19e9fbdf786b995649e5e2**.
- B198 APK [Run 44945727664](https://github.com/vaishnavi596/volume-king/actions/runs/44945727664), job 136972497261: same package, versionCode 198, actual `Android Debug` SHA-256 **9e98159e0429a718f1d9472a9d191f79f97871d4609961a817ede6d71580bc25**.
- Difference proven from actual job logs. Workflow `.github/workflows/v1-pure-original-clone-apk.yml` creates ephemeral `clone.jks` by `keytool -genkeypair` each run, exports `FLET_ANDROID_SIGNING_KEY_STORE` variables, yet the final APK identifies itself as **Android Debug**, not `CN=BOT KING B3 CLONE TEST`. This indicates configured release keystore is not actually used and/or Flutter fallback to per-run generated debug cert; root subcause requires build/signing inspection. Both v1/v2 signature scheme verification successful **does not mean signing identity stable**. Android generally rejects an in-place upgrade to the same package signed with a different certificate. Never ask operator to uninstall without a local data preservation/migration plan.
- Gate: pin one persistent protected signing identity stored via authorized secure CI secret (never commit the keystore or passwords), verify apksigner cert SHA-256 against an expected fingerprint, and test install-update B197→B198-equivalent safely on sacrificial device/test data before claiming upgrade support. Existing packages signed with mismatched keys will still need a controlled migration route.
