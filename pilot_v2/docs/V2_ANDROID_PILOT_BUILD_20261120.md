# V2 isolated Android pilot build — production release NOT implied

- Trigger: on the V2 branch's first commit of `.github/workflows/botking-v2-android-pilot.yml` (push) and later manual dispatch when the workflow is visible in Actions. GitHub's workflow engine must confirm execution; creating this source is not a completed APK build.
- The workflow runs compile, all V2 offline tests, one-shot feature audit and static identity preflight; then builds one Flet 0.25.2 / pyjnius 1.6.1 Android **offline pilot APK** from `pilot_v2/android_app`. Explicit `--project bot_king_v2 --org com.botking` targets `com.botking.bot_king_v2`, independent of the V1 `com.botking.bot_king` package. It must verify actual APK via aapt (package/version/label) and apksigner, not metadata assertions alone.
- The pilot signing keystore is an **ephemeral non-production test key** generated on the runner only. It is never committed/uploaded; this means APK upgrades cannot be signed with the same key after the runner disappears — future upgrade will require uninstall/reinstall of V2 pilot or replacement with a protected stable V2 signing keystore. Never uninstall V1. It does not have protected Dhan secrets, live broker data, or a V2 Oracle service; it must display OFFLINE/WAIT rather than fake values.
- When the Actions run is green, retrieve the `bot-king-v2-offline-pilot-apk-2.0.100` artifact from the workflow run. Confirm `com.botking.bot_king_v2` in the binary metadata and install alongside V1, then verify both separate launchers, independent local settings/rosters, V1 remains usable, Android Keystore direct JNI, owner public SPKI and signed login. No claim of physical device PASS before that test.
- Important root cause: `project.name = bot-king-v2-pilot` in the older pyproject might generate a distinct application ID if the CLI project override is not honored; the workflow **fails closed** on real binary mismatch. Do not rename or patch V1 to resolve this; fix only isolated V2 packaging if the build log demonstrates mismatch.
- If GitHub build is blocked by toolchain/permissions/Android dependency compatibility, inspect the exact failed step and repair the bounded V2 build flow. If only signing is blocked, do NOT use V1 keystore or disclose any key. Do not switch on V2 production merely because the candidate APK builds.
